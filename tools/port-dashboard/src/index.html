KEY ENGINEERING DIFFERENCE
x86-64 instructions are variable-length (1–15 bytes). REX prefixes, ModR/M bytes, SIB bytes — every instruction is a different size. Branch offsets are in bytes.

ARM64 instructions are always exactly 4 bytes. No prefixes. Fields are packed into fixed bit positions. Branch offsets are in instructions (divide byte offset by 4).

Consequence for control.fs: x86 patch-rel32 writes 4 bytes at offset. ARM64 patch-branch must read the 32-bit instruction, mask out the offset field, insert the new offset (in instructions, not bytes), and write the instruction back. The bit field depends on the instruction type (B uses bits 25:0, B.cond uses bits 23:5, CBZ uses bits 23:5).

WHAT THIS MEANS FOR io.fs
x86 gen-emit (current): 24 bytes — push rbx, push rcx (conditional), push rax, mov eax/edi/rsi/edx, syscall, pop×3, pop-val
ARM64 gen-emit (target): ~20 bytes — mov X0/X1/X2/X16 from stack regs, svc, pop-val. No save/restore.

The ARM64 version is both shorter and simpler because syscalls don't destroy our stack registers. The conditional save-rbx/save-rcx logic in the x86 version (controlled by stack-depth@) disappears entirely.

Branch Patching — The Critical Difference

x86-64 patch-rel32

Forward branch patching

JZ rel32 = 0F 84 + 4-byte signed displacement
Displacement = target_addr - (instruction_addr + 6)

To patch: Write 4 bytes at the displacement field.
Simple: target from - swap 4 - code-buf + d!
The displacement field is separate bytes after the opcode.
→

ARM64 patch-branch

Forward branch patching

B.EQ offset = single 32-bit word
Offset is in bits [23:5] — a 19-bit signed field (±1MB range)
Offset is in instructions not bytes: divide by 4

To patch:
  1. Read 32-bit instruction from code-buf
  2. Mask out bits [23:5] (the offset field)
  3. Calculate: (target - insn_addr) / 4
  4. Insert into bits [23:5]
  5. Write 32-bit instruction back

Different instruction types use different bit fields:
• B: bits [25:0] — 26-bit, ±128MB
• B.cond: bits [23:5] — 19-bit, ±1MB
• CBZ/CBNZ: bits [23:5] — 19-bit, ±1MB

ELF64 (current) → Mach-O (target)

ELF64 — Linux x86-64

176 bytes total header. Simple.
+0x00 ELF Header (64 bytes) \x7fELF magic, e_entry=0x4000B0
+0x40 PHDR 1: Code (56 bytes) PT_LOAD RX @ 0x400000
+0x78 PHDR 2: Data (56 bytes) PT_LOAD RW @ 0x800000, 2MB
+0xB0 Code starts here entry point = header end
Virtual memory layout:
0x400000 — Code (RX), size = 176 + code-pos
0x800000 — Data (RW), 2MB BSS (zeroed by kernel)
0x900000 — Data stack (grows down from here)
0x980000 — Return stack (grows down from here)
→

MACH-O — macOS ARM64

~320-400 bytes header. More load commands.
+0x00 Mach-O Header (32 bytes) MH_MAGIC_64, CPU_TYPE_ARM64
+0x20 LC_SEGMENT_64 __PAGEZERO 72 bytes, NULL page trap
+0x68 LC_SEGMENT_64 __TEXT 72 bytes + section headers
~+0xE0 LC_SEGMENT_64 __DATA 72 bytes + section headers
~+0x140 LC_MAIN 24 bytes, entryoff + stacksize
Virtual memory layout (page-aligned, 16KB):
0x000000000 — __PAGEZERO (4GB null trap)
0x100000000 — __TEXT (RX), code starts at header end
0x100008000 — __DATA (RW) est.
Must be page-aligned to 16KB on Apple Silicon!
KEY DIFFERENCES
1. Page size: ELF uses 4KB pages (0x1000). Mach-O on Apple Silicon uses 16KB (0x4000).
2. Entry point: ELF e_entry is a virtual address. Mach-O LC_MAIN uses a file offset.
3. Code signing: ELF needs nothing. Mach-O must be ad-hoc signed: codesign -s - binary.
4. Null page: Mach-O requires __PAGEZERO (typically 4GB). ELF doesn't.
5. Data addresses: ELF uses absolute addresses (0x800000). Mach-O needs ADRP+ADD (PC-relative) or absolute loads at higher addresses (~0x100008000).
6. Header complexity: ELF: 2 program headers = 176 bytes. Mach-O: 4+ load commands, section headers = ~400 bytes.

Data Addressing — The Subtle Trap

On x86, DATA-BASE is 0x800000 and accessed with absolute addresses:

mov rax, [0x800000 + offset]  ; absolute 32-bit address, sign-extended

On ARM64, addresses are 48+ bits and can't fit in a single instruction. Two options:

; Option A: PC-relative (2 insns, position-independent)
ADRP  X9, data_page       ; load page address (4KB aligned)
ADD   X9, X9, #offset     ; add page offset
LDR   X19, [X9]           ; load value

; Option B: Absolute (2-4 insns, simpler for us)
MOVZ  X9, #lower16
MOVK  X9, #upper16, LSL #16
MOVK  X9, #upper32, LSL #32  ; if needed
LDR   X19, [X9]

Decision: Start with Option B (MOVZ/MOVK absolute addresses). It's more bytes but simpler to implement. Optimize to ADRP later if code size matters.

Architecture Decisions LOCKED

DecisionValueRationale
🔒 TOS Register X19 Callee-saved. Survives function calls. No need for save/restore around SVC.
🔒 NOS Register X20 Callee-saved. Paired with TOS for STP/LDP efficiency.
🔒 3rd Register X21 Callee-saved. Three stack registers cover most Forth word needs.
🔒 Stack Pointer X22 Callee-saved. Points to memory data stack (not hardware SP).
🔒 Return Stack X28 Callee-saved. Dedicated return stack pointer (like x86 R12).
🔒 Scratch Registers X9-X15 Caller-saved temporaries. 7 available vs x86's 2-3. Major optimization advantage.
🔒 CODE-BASE 0x100000000 macOS standard __TEXT segment virtual address for 64-bit binaries.
🔒 Binary Format Mach-O (LC_MAIN dynamic) NOT static. Requires dyld, libSystem.B.dylib stub. LC_UNIXTHREAD rejected.
🔒 Code Signing Ad-hoc (codesign -f -s -) Required for macOS ARM64 execution. 16-byte padding reserved for signature insertion.
🔒 Instruction Size Fixed 32-bit All ARM64 instructions are exactly 4 bytes. No variable-length decoding. emit32 replaces c,/d,
🔒 System Calls SVC #0x80 macOS ARM64 uses SVC not SWI. Syscall numbers are 0x2000000+N (Unix class prefix).
🔒 Build Strategy Ground-up (not line-by-line port) ARM64 files written from scratch. x86 files are REFERENCE, not SOURCE. Different ISAs need different approaches.

Optimization Pipeline

Shannon applies 5 optimization passes during compilation. Each pass operates during code generation (single-pass over the token stream), not as separate compilation stages.

A. Constant Folding

Evaluate compile-time constants. 3 4 + 2 * → 14
opt-fold.fs (114 lines)

B. Literal Fusion

Fuse constant + op into immediate instruction. x 8 * → shl 3
opt-fuse.fs (95 lines)

C. Swap Elimination

Absorb swaps before commutative ops. swap + → +
opt-swap.fs (60 lines)

D. Dup Fusion

Defer dup for 0= fusion. dup 0= if → single test+branch
compile.fs (dup-pending)

E. Compare Fusion

Fuse compare + branch. 0= if → test+jz
compile.fs (cmp-pending)

ARM64 Opportunity

Constant folding is architecture-independent — it operates on the compile-time stack, not on machine instructions. The fold pass works identically on ARM64. Only the final emit-lit changes (MOVZ/MOVK sequence instead of MOV reg, imm64).

ARM64 Adaptation

ARM64 has rich immediate forms: ADD Xd, Xn, #imm12 (12-bit), shifted immediates, and bitmask immediates for AND/OR/XOR. The fusion logic stays the same; only the emit functions change. ARM64 actually has more immediate encoding options than x86.

ARM64 Advantage

ARM64 has 3-operand instructions (ADD Xd, Xn, Xm), so many "swap" situations simply become operand reordering in the instruction encoding. The swap elimination pass becomes even more effective — most swaps can be absorbed by swapping register operands in the ARM64 instruction.

ARM64 Adaptation

ARM64 has condition codes set by CMP and conditional branch instructions (B.EQ, B.NE, B.LT, etc.). The fusion pattern maps directly: CMP X19, X20; B.GE target. ARM64 also has CBZ and CBNZ (compare-and-branch-if-zero/nonzero) which fuse even more tightly.

ARM64-Specific Optimization Opportunities

ARM64 opens new optimization paths not available on x86-64.

STP/LDP Paired Operations

ARM64 can store/load two 64-bit registers in a single instruction. push-val can use STP X19, X20, [X22, #-16]! to push TOS+NOS simultaneously. x86 requires two separate mov [r15], rax; sub r15, 8 sequences.

CBZ/CBNZ (Compare-Branch-Zero)

0= if becomes a single CBZ X19, target instruction (4 bytes). x86 needs test rax, rax; jz target (5+ bytes, 2 instructions).

7 Scratch Registers

ARM64 has X9-X15 as caller-saved temporaries (7 registers). x86 has only RAX, RCX, RDX as easily available scratch (~3). This means fewer spills to memory during complex expressions.

Bitmask Immediates

ARM64 AND/OR/EOR accept bitmask immediates that encode repeating patterns. and rax, 0xFF (x86: 5-7 bytes) becomes AND X19, X19, #0xFF (4 bytes). Many mask operations become single instructions.

Conditional Select (CSEL)

ARM64 CSEL Xd, Xn, Xm, cond replaces entire if/then/else sequences for simple value selection. min and max become: CMP X19, X20; CSEL X19, X19, X20, LT (2 instructions, no branch).

MADD/MSUB (Multiply-Add)

ARM64 MADD Xd, Xn, Xm, Xa computes Xa + Xn*Xm in one instruction. Patterns like a b * c + could be fused to a single MADD. x86 has no equivalent (requires separate mul + add).
